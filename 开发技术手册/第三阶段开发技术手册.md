## 一、先说简单结论

第三阶段不是开发 Agent，也不是增加新的陪伴功能。

这一阶段只解决两类基础问题：

1. 把现在保存在本地 JSON 文件里的学习数据迁移到可靠数据库。
2. 把“邀请码”和“用户账号”分开，让每个人真正拥有独立账号和独立数据。

可以把它理解成：

```text
现在：邀请码既像门票，又被当成用户身份证
      学习数据保存在单台服务的本地文件里

第三阶段后：邀请码只负责允许注册
            用户名和密码负责登录
            独立用户 ID 负责隔离数据
            数据库负责可靠保存数据
```

只有这一阶段全部验收通过，项目才允许进入 P1 的 Agent Harness 建设。

## 六、目标架构

### 6.1 改造前

```text
API 路由
→ 业务 Service
→ JsonStore
→ 每个邀请码哈希对应的本地目录
→ history.json / goal.json / stats.json
```

主要问题：

- 多个服务实例看不到同一份本地文件。
- 一个邀请码只能映射成一个用户目录。
- Token 无法在服务端单独撤销。
- 文件迁移、关联查询和事务能力有限。

### 6.2 改造后

```text
FastAPI 路由
→ 身份依赖或业务 Service
→ Repository
→ 请求级 SQLAlchemy Session
→ SQLite（本地）/ PostgreSQL（正式环境）
```

各层职责：

| 层级 | 只负责什么 | 不能做什么 |
|---|---|---|
| API 路由 | 接收参数、鉴权、返回响应 | 不直接写 SQL |
| Service | 处理注册、结算、统计等业务规则 | 不依赖具体数据库方言 |
| Repository | 查询、保存、唯一约束冲突转换 | 不处理页面文案 |
| Model | 描述数据库表和关系 | 不承担业务流程 |
| Migration | 管理数据库版本升级和降级 | 不读取生产秘密 |
| Importer | 读取旧 JSON、转换、核对和报告 | 不删除或覆盖源文件 |

## 七、数据库技术方案

### 7.1 数据库与访问方式

推荐采用：

| 环境 | 数据库 | 连接方式 |
|---|---|---|
| 本地开发 | SQLite 文件 | `sqlite+pysqlite:///...` |
| 自动单元测试 | 临时 SQLite 文件 | 每个测试独立创建和清理 |
| PostgreSQL 集成测试 | 隔离的临时 PostgreSQL | 禁止使用生产库 |
| 正式环境 | PostgreSQL | `postgresql+psycopg://...` |

推荐使用同步 SQLAlchemy Session，理由：

- 当前 JSON Service 本身是同步代码，迁移成本更低。
- 当前产品数据库负载较小，不需要为了“看起来高级”引入异步数据库复杂度。
- 数据库路由可以使用 FastAPI 同步路径函数，由框架在线程池运行。
- 聊天和 TTS 等外部网络请求继续保持异步，不必整体改写。

强制规则：

- 每个 HTTP 请求创建独立 Session，请求结束后关闭。
- 一个 Session 不能在多个线程或并发任务之间共享。
- 写操作必须在明确的事务中完成。
- 失败必须回滚，不允许捕获异常后继续提交。
- 生产环境不能使用 SQLite 作为共享数据库。
- 正式数据库结构不能通过应用启动时 `create_all()` 自动改变。
- 所有正式结构变化必须来自 Alembic revision。

### 7.2 配置项

建议新增或调整：

| 配置 | 用途 | 安全要求 |
|---|---|---|
| `DATABASE_URL` | 当前环境数据库地址 | 生产环境必填，不能打印完整值 |
| `DATABASE_POOL_SIZE` | PostgreSQL 连接池大小 | 根据平台实例数和数据库上限设置 |
| `DATABASE_POOL_TIMEOUT` | 获取连接等待时间 | 超时返回可识别错误 |
| `AUTH_TOKEN_TTL_SECONDS` | 登录有效期 | 推荐默认保持 30 天，可配置 |
| `INVITE_CODE_PEPPER` | 邀请码摘要密钥 | 与数据库分开保存，不进入 Git |
| `ALLOW_LEGACY_TOKENS` | 是否临时接受旧 Token | 仅迁移认领窗口使用，正式关闭 |
| `STORAGE_BACKEND` | 迁移期读取模式 | 只允许明确枚举值，不能静默回退 |

生产启动校验：

- 缺少 `DATABASE_URL` 时拒绝启动。
- 生产环境检测到 SQLite 地址时拒绝启动。
- 使用默认 `AUTH_SECRET` 或默认邀请码摘要密钥时拒绝启动。
- 错误信息只能说“数据库配置无效”，不能回显账号和密码。

### 7.3 数据库迁移规则

- Alembic 保存唯一、连续的 revision 链。
- 每个 revision 都必须人工检查生成结果。
- 每个 revision 都要有 `upgrade()`。
- 能安全降级的结构变化应提供 `downgrade()`。
- 会删除数据的 downgrade 不能被包装成“安全回滚”。
- 自动测试必须从空数据库执行 `upgrade head`。
- 自动测试必须验证当前 revision 与代码模型一致。
- 应用启动只检查数据库是否已升级，不自动执行升级。

## 八、数据库表设计

### 8.1 核心表

| 表 | 作用 | 本阶段是否启用业务写入 |
|---|---|---:|
| `users` | 独立用户身份 | 是 |
| `invite_codes` | 邀请码规则和状态 | 是 |
| `invite_redemptions` | 记录邀请码被哪个用户使用 | 是 |
| `auth_sessions` | 可过期、可撤销的登录会话 | 是 |
| `study_sessions` | 每轮专注的唯一记录 | 是 |
| `daily_study_records` | 每日番茄数和总分钟数 | 是 |
| `daily_goals` | 按用户和日期保存目标 | 是 |
| `chat_sessions` | 为后续会话记忆预留稳定归属 | 否，仅建基础结构 |
| `chat_messages` | 为后续聊天持久化预留 | 否，仅建基础结构 |
| `user_preferences` | 保存可同步的用户偏好 | 暂不接入现有页面 |
| `agent_events` | 为后续 Agent 轨迹预留 | 否，不提前记录 Agent 事件 |
| `migration_runs` | 记录迁移批次、校验和和结果 | 是 |

### 8.2 `users`

建议字段：

| 字段 | 规则 |
|---|---|
| `id` | UUID 主键，由后端生成 |
| `username` | 用户看到的登录名 |
| `username_normalized` | 规范化后唯一，用于登录查询 |
| `password_hash` | Argon2 哈希；旧待认领用户可暂时为空 |
| `timezone` | 默认 `Asia/Shanghai` |
| `status` | `active`、`legacy_unclaimed`、`disabled` |
| `legacy_user_key` | 旧 JSON 目录标识，可为空且唯一 |
| `created_at`、`updated_at` | 使用带时区时间戳 |

规则：

- 用户名规范化后必须唯一。
- API 永远不能返回 `password_hash`。
- 用户 ID 由后端生成，不能接受前端指定。
- 用户停用后，其所有 Token 立即失效。

### 8.3 `invite_codes` 与 `invite_redemptions`

邀请码字段至少包含：

- `id`。
- `code_digest`：邀请码摘要，不保存可直接使用的明文。
- `max_uses`：最多可使用次数。
- `used_count`：已使用次数。
- `expires_at`：失效时间，可为空。
- `disabled_at`：停用时间，可为空。
- `created_at`。

兑换记录保存：邀请码 ID、用户 ID、兑换时间，并建立唯一约束。

一次注册必须在同一个数据库事务中完成：

```text
校验邀请码未过期且未停用
→ 原子占用一次使用次数
→ 创建独立用户
→ 写入兑换记录
→ 创建登录会话
→ 一次性提交
```

任何一步失败，全部回滚，不能出现“次数扣了但用户没创建”的情况。

### 8.4 `auth_sessions`

建议字段：

| 字段 | 规则 |
|---|---|
| `id` | 会话 UUID |
| `user_id` | 外键，指向用户 |
| `token_hash` | Token 的 SHA-256 摘要，唯一 |
| `expires_at` | 到期时间 |
| `revoked_at` | 退出或管理员撤销时间，可为空 |
| `created_at` | 创建时间 |
| `last_seen_at` | 最近使用时间，按需要低频更新 |

后端只在登录成功时把明文 Token 返回一次，数据库只存摘要。以后每次请求先计算摘要，再查询会话是否有效。

### 8.5 学习数据表

`study_sessions` 至少保存：

- 内部主键。
- `user_id`。
- 前端生成的 `client_session_id`。
- 开始时间、结束时间和完成时间。
- 专注分钟数。
- 状态。
- 数据来源：正常完成或旧数据导入。
- 创建时间。

必须建立：

```text
UNIQUE(user_id, client_session_id)
```

这条数据库唯一约束是防止重复记账的最终保护，不能只依靠 Python 先查询再判断。

`daily_study_records` 至少保存：

- `user_id`。
- `study_date`。
- `tomato_count`。
- `minutes`。
- `updated_at`。

必须建立：

```text
UNIQUE(user_id, study_date)
```

完成一轮专注时，插入 `study_sessions` 和更新 `daily_study_records` 必须在同一个事务中。重复 `client_session_id` 返回当前统计，不再增加每日数据。

### 8.6 `daily_goals`

至少保存用户 ID、目标日期、目标文字、创建时间和更新时间，并建立：

```text
UNIQUE(user_id, goal_date)
```

日期由后端根据用户时区计算，不能相信前端传入的“今天”。

### 8.7 约束与索引

除主键外至少需要：

- 用户规范化登录名唯一索引。
- 邀请码摘要唯一索引。
- Token 摘要唯一索引。
- 用户与客户端 sessionId 联合唯一索引。
- 用户与目标日期联合唯一索引。
- 用户与学习日期联合唯一索引。
- `auth_sessions(user_id, revoked_at, expires_at)` 查询索引。
- `study_sessions(user_id, completed_at)` 查询索引。

分钟数、番茄数和邀请码次数应增加非负约束。必要字段使用 `NOT NULL`，不能用大量可空字段掩盖数据问题。

## 九、P0-C01：建立数据库结构

### 9.1 实施步骤

1. 在独立第三阶段分支中增加数据库依赖和配置校验。
2. 建立 engine、Session factory 和 FastAPI Session 依赖。
3. 建立 SQLAlchemy Declarative Base 与模型。
4. 初始化 Alembic。
5. 创建第一版数据库 migration。
6. 从空 SQLite 执行 upgrade、downgrade、再次 upgrade。
7. 在隔离 PostgreSQL 上执行同样检查。
8. 建立 Repository 接口和实现。
9. 先写 Repository 测试，不立即切换全部 API。

### 9.2 Repository 边界

建议最少包含：

| Repository | 负责内容 |
|---|---|
| `UserRepository` | 用户创建、查询、状态更新 |
| `InviteRepository` | 邀请码验证、原子使用和兑换记录 |
| `AuthSessionRepository` | 会话创建、查询、撤销和过期判断 |
| `StudyRepository` | 幂等完成、每日统计、历史查询 |
| `GoalRepository` | 按用户和日期读写目标 |
| `MigrationRepository` | 迁移批次与源校验记录 |

业务 Service 不能知道 SQLAlchemy 查询细节。测试时可以替换 Repository，但正式实现必须依赖数据库约束。

### 9.3 P0-C01 验收标准

- [ ] 空数据库可以通过 Alembic 一次升级到最新版本。
- [ ] SQLite 和 PostgreSQL 都能创建相同业务结构。
- [ ] 每个请求使用独立 Session。
- [ ] 写入失败会回滚。
- [ ] 两个数据库 Session 能读取同一份已提交数据。
- [ ] 并发提交相同 `client_session_id` 最终只有一条记录。
- [ ] API 层没有直接拼接 SQL。
- [ ] 生产环境配置成 SQLite 时拒绝启动。

## 十、P0-C02：迁移现有 JSON 数据

### 10.1 迁移事实来源

| 旧文件 | 处理方式 |
|---|---|
| `history.json` | 主要事实来源，迁移每日记录和 completedSessions |
| `goal.json` | 迁移非空目标，但需要确认目标日期规则 |
| `stats.json` | 只做总数交叉核对，不直接导入 |
| 不认识的 JSON | 跳过并记录，不猜测含义 |
| 损坏的 JSON | 标记失败，保留原文件，禁止静默当成空数据 |

### 10.2 四种运行模式

迁移工具必须明确区分：

| 模式 | 是否写数据库 | 用途 |
|---|---:|---|
| `scan` | 否 | 只统计目录、文件版本和异常数量 |
| `dry-run` | 否 | 完成解析和映射，生成预计结果 |
| `import` | 是 | 在确认备份后正式导入 |
| `verify` | 否 | 对比源 JSON 与数据库汇总 |

默认必须是 `dry-run` 或要求显式指定模式，不能运行命令就直接导入。

### 10.3 迁移幂等规则

- 每个源文件计算校验和。
- `migration_runs` 记录迁移批次、源标识、校验和、状态和数量。
- 同一源校验和成功导入后再次执行，只能显示“已跳过”。
- 每日记录按用户和日期唯一。
- completed session 按用户和 sessionId 唯一。
- 导入已存在且内容相同的数据时跳过。
- 导入已存在但内容冲突的数据时停止，不能覆盖。

### 10.4 每日历史迁移

对于 `history.json`：

1. 兼容 schema v1 和 v2。
2. 先复用现有规范化逻辑处理合法字段。
3. `days` 直接导入每日统计表。
4. `completedSessions` 导入专注表，用于保留幂等编号。
5. 导入 completed session 时不能再次增加已从 `days` 导入的每日总数。
6. 如果 session 明细之和与 daily 汇总不同，保留 daily 汇总作为历史事实，并在报告中记录差异。
7. 未来日期、负数、非法日期和非法分钟数单独报告，不静默修正为真实学习记录。

### 10.5 旧目标迁移

当前 `goal.json` 没有保存目标日期，无法准确判断它属于哪一天。

推荐方案：

- 非空旧目标导入为“迁移执行当天”的目标。
- 标记来源为 `legacy_import`。
- 在核对报告中列出导入数量。
- 不根据文件修改时间猜测日期。

此规则必须由用户确认后才能执行。

### 10.6 迁移报告

报告只记录汇总，不输出聊天内容、邀请码、Token 或完整目录身份标识。

至少包含：

- 扫描用户目录数。
- 成功、跳过、失败用户数。
- 每日记录数。
- 番茄总数。
- 专注总分钟数。
- sessionId 总数。
- 非空目标数。
- 损坏文件和冲突数量。
- 源校验和与迁移批次号。

### 10.7 P0-C02 验收标准

- [ ] 正式迁移前已生成可恢复备份。
- [ ] dry-run 不修改数据库和源文件。
- [ ] 导入前后用户目录数、番茄总数和总分钟数一致。
- [ ] 重复导入不会产生重复数据。
- [ ] 迁移失败不会删除或改写源 JSON。
- [ ] 损坏和冲突数据有清晰报告。
- [ ] 不在终端和报告中泄露真实秘密或完整用户内容。

## 十一、P0-C03：邀请码与用户账号分离

### 11.1 推荐登录方案

推荐本阶段使用：

```text
注册：邀请码 + 用户自设登录名 + 用户自设密码
登录：登录名 + 密码
鉴权：可撤销的随机 Token
```

原因：

- 不依赖短信、邮件或第三方付费服务。
- 两个人可以使用同一邀请码，各自创建不同账号。
- 改动范围可控，适合当前小规模 MVP。

限制：

- 暂不具备自助找回密码能力。
- 忘记密码时只能走受控的管理员重置流程。
- 不能把登录名宣传成已经验证的邮箱或手机号。

### 11.2 密码规则

- 明文密码只在注册和登录请求中短暂存在。
- 数据库只保存 Argon2 哈希。
- 不自己设计加密算法。
- 登录名不存在时仍执行一次虚拟密码校验，减少账号枚举时序差异。
- 登录失败统一返回“账号或密码错误”，不暴露账号是否存在。
- 密码、密码哈希不能进入日志、错误响应或测试快照。
- 管理员只能触发重置，不能读取用户原密码。

### 11.3 Token 方案

推荐继续保持前端 Bearer Token 调用方式，但把 Token 改为数据库可撤销的随机凭证：

1. 后端使用安全随机数生成 Token。
2. 明文 Token 只返回给浏览器一次。
3. 数据库只保存 Token 的 SHA-256 摘要。
4. 每次请求检查用户、过期时间和撤销时间。
5. 退出登录时撤销当前会话。
6. 用户被停用时全部会话失效。

本阶段不同时改成 Cookie 登录，避免把数据库迁移、账号迁移和浏览器鉴权协议三件高风险改动混在一起。Cookie 方案可在公开推广前单独评审。

### 11.4 API 调整

建议新增或调整：

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/v1/auth/register` | 使用邀请码、登录名和密码创建独立账号 |
| POST | `/api/v1/auth/login` | 使用登录名和密码登录 |
| GET | `/api/v1/auth/session` | 验证当前 Token，保持现有用途 |
| POST | `/api/v1/auth/logout` | 在服务端撤销当前 Token |
| POST | `/api/v1/auth/legacy-claim` | 在确认需要时认领旧账号，仅迁移窗口启用 |

邀请码管理不提供公开网页接口，先通过受控 CLI 创建、停用和查看汇总。CLI 不得显示邀请码明文历史值。

### 11.5 旧用户数据认领

这是第三阶段最重要的产品决策。

当前旧数据按“邀请码哈希”分目录。如果多人曾使用同一个邀请码，他们的数据已经混在一起，系统无法自动判断每条记录属于谁。

因此不能承诺自动拆分旧共享数据。推荐处理方式：

| 数据情况 | 推荐处理 |
|---|---|
| 只有开发测试数据 | 迁移到隔离测试账号或只保留备份，不提供认领 |
| 一个目录确定只属于一个真实用户 | 创建 `legacy_unclaimed` 用户，通过旧浏览器 Token 完成一次认领 |
| 一个目录可能由多人共用 | 暂停自动认领，由产品方决定整体归属或只保留匿名汇总 |
| 用户已丢失旧 Token | 不能仅凭原邀请码认领，走人工核验流程 |

旧 Token 兼容只能在明确的短期认领窗口启用。认领结束后关闭 `ALLOW_LEGACY_TOKENS`，旧 Token 不再访问业务 API。

### 11.6 注册并发与邀请码次数

同一个邀请码最后一次名额被两个人同时使用时，只能有一个事务成功。不能采用：

```text
先查 used_count
→ Python 中加一
→ 再保存
```

必须依靠数据库事务、条件更新和唯一约束完成原子占用。

### 11.7 P0-C03 验收标准

- [ ] 两个人使用同一邀请码可以创建不同用户 ID。
- [ ] 两个账号的学习数据完全隔离。
- [ ] 失效、停用或次数耗尽的邀请码不能注册。
- [ ] 已注册用户不因原邀请码停用而无法登录。
- [ ] 相同登录名不能重复注册。
- [ ] 数据库中没有明文密码和明文 Token。
- [ ] 退出登录后原 Token 立即失效。
- [ ] 过期 Token 和撤销 Token 都返回 401。
- [ ] 注册事务失败时邀请码次数不会被错误扣除。
- [ ] 旧数据认领不会让他人仅凭邀请码取得历史数据。

## 十二、P0-C04：数据切换与回滚

### 12.1 推荐切换方式

推荐使用短维护窗口，不实现长期双写。

原因：JSON 与数据库长期双写会制造两份事实来源，增加漏写、顺序和回滚问题。当前项目规模更适合一次可验证切换。

切换顺序：

```text
停止正式写入
→ 备份 JSON 和数据库
→ 执行 Alembic upgrade
→ 运行 JSON dry-run
→ 正式导入
→ 运行 verify 核对
→ 部署数据库版后端
→ 部署新登录页前端
→ 执行冒烟测试
→ 恢复写入
→ JSON 进入只读保留状态
```

本手册只定义步骤，不授权实际生产切换。

### 12.2 存储模式

迁移期间建议使用明确配置：

| 模式 | 读取 | 写入 | 使用阶段 |
|---|---|---|---|
| `json` | JSON | JSON | 切换前旧版本 |
| `database` | 数据库 | 数据库 | 正式切换后 |
| `compare` | 正式结果来自数据库，同时只读核对 JSON | 数据库 | 测试和短期验证 |

禁止发生：

- 数据库失败时静默写回 JSON。
- 同一个正式请求同时写 JSON 和数据库却不检查结果。
- 已经产生数据库新数据后直接把线上切回旧 JSON。

### 12.3 回滚边界

切换前回滚：

- 停止导入。
- 回滚未完成事务。
- 保留原 JSON 和报告。
- 修正脚本后重新 dry-run。

切换后但尚未恢复用户写入：

- 可以回退应用版本和数据库 revision。
- 再次核对 JSON 与数据库。

恢复用户写入后：

- 数据库已经产生新事实，不能直接切回旧 JSON。
- 应优先回退到“仍然支持当前数据库结构”的上一应用提交。
- 如果必须回到 JSON，必须先导出并人工核对新增数据库记录；不能直接覆盖。
- 数据库故障时进入维护状态，不允许假成功或把数据悄悄写到实例磁盘。

### 12.4 健康检查

- `GET /health` 继续作为进程存活检查，不执行重查询。
- 建议增加 `GET /ready` 检查数据库可连接且 migration revision 正确。
- readiness 失败时实例不接收业务流量。
- 健康接口不能返回数据库地址、账号或错误堆栈。

### 12.5 P0-C04 验收标准

- [ ] 统计、历史、目标、专注完成和身份接口全部使用数据库。
- [ ] 正式业务代码不再向 JSON 写入新数据。
- [ ] 服务重启和重新部署后数据仍存在。
- [ ] 两个后端实例可以读取同一份已提交数据。
- [ ] 数据库不可用时写接口明确失败，不返回假成功。
- [ ] compare 模式的匿名样本结果一致。
- [ ] 至少完成一次隔离环境切换与回滚演练。
- [ ] 旧 JSON 被只读保留，没有删除。

## 十三、前端适配

第三阶段前端只调整身份流程，不重做 UI。

### 13.1 登录页

登录页需要区分：

- 已有账号：登录名 + 密码。
- 新用户：邀请码 + 登录名 + 密码 + 确认密码。

新流程：


网络完全不可用时，前端可以先完成本地退出并提示“服务端会话可能尚未撤销”；不能伪装成服务端撤销成功。

- `/api/v1/stats`
- `/api/v1/stats/complete`
- `/api/v1/history`

## 十六、自动测试方案

## 十七、人工验收流程

只使用隔离测试环境和测试数据：

1. 从空数据库执行 Alembic upgrade。
2. 创建一个最多可用两次的测试邀请码。
3. 使用同一邀请码注册用户 A 和用户 B。
4. 确认两人的用户 ID 不同。
5. 用户 A 完成一次专注并设置目标。
6. 用户 B 登录，确认看不到用户 A 的目标和学习记录。
7. 用户 A 退出，确认原 Token 不能继续访问。
8. 停用邀请码，确认不能继续注册。
9. 确认已注册的用户 A、B 仍能登录。
10. 对匿名 JSON 样本执行 scan 和 dry-run。
11. 备份后执行正式导入和 verify。
12. 再次执行导入，确认全部跳过且没有重复。
13. 重启后端，确认账号和学习数据仍然存在。
14. 模拟数据库断开，确认写入明确失败而非假成功。
15. 在隔离环境演练一次切换前回滚。
16. 在隔离环境演练一次切换后的数据库兼容回退。
17. 运行完整 `./scripts/verify.sh`。
18. 确认没有触碰真实 `.env`、真实数据库和真实用户数据。

## 十八、安全与隐私底线

- 数据库密码、邀请码摘要密钥和 Token 不进入 Git。
- 数据库连接错误不回显连接串。
- 密码不写日志，不保存明文，不可逆加密后冒充哈希。
- Token 只保存摘要。
- 邀请码不作为用户 ID，不出现在公开 README。
- 用户 ID 只能来自已验证会话，不能相信请求体传入的 userId。
- 所有 Repository 查询必须带当前用户范围。
- 迁移报告只保存汇总和脱敏源标识。
- 备份文件不能提交 Git，也不能放在前端可访问目录。
- 真实数据迁移属于生产变更，必须另行获得明确授权。
- 数据库不可用时宁可明确失败，也不能回退到不可靠本地文件并返回成功。

## 十九、风险与回退方案

| 风险 | 预防措施 | 回退方式 |
|---|---|---|
| 迁移少数据 | 源校验和、总数核对、匿名样本演练 | 停止切换，保留 JSON，修复后重跑 |
| 迁移重复数据 | migration_runs、唯一约束、幂等导入 | 回滚本批事务，不手工删源文件 |
| session 明细与每日总数不一致 | daily 作为历史汇总事实，差异写报告 | 人工确认后再切换 |
| 同邀请码旧数据混合 | 开发前完成真实数据审计 | 不自动拆分，暂停认领 |
| 邀请码超用 | 事务内原子占用和兑换记录 | 回滚注册事务 |
| 重复专注结算 | 数据库联合唯一约束 | 返回当前统计，不重复增加 |
| Token 泄露 | 只存摘要、可撤销、可停用用户 | 撤销对应会话或全部会话 |
| PostgreSQL 不可用 | readiness、超时、明确失败 | 维护模式或 DB 兼容版本回退 |
| SQLite 测试通过但 PostgreSQL 失败 | 增加 PostgreSQL 集成测试 | 不进入切换步骤 |
| 新旧前端登录协议不一致 | 联调版本和明确发布顺序 | 回退到同一协议版本组合 |
| 切换后直接回 JSON导致新数据丢失 | 禁止静默回退，保留 DB 兼容发布 | 先导出和核对新数据 |
| 依赖版本冲突 | 安装后锁定已验证兼容版本 | 回退依赖提交和迁移提交 |
