> 编制依据：《开发排期手册.md》《项目改进迭代方案.md》《后端开发技术适配声明.md》《第六阶段验收记录.md》

## 一、先说简单结论

前六个阶段已经把产品的可靠性、账号数据、Agent 主闭环、会话记忆、受控长期记忆、情绪安全和脱敏轨迹建立起来。

第七阶段进入 P2，目标不是让模型获得更多自主权，而是把已经存在的学习行为变成**可控的主动陪伴、可解释的产品指标、基于真实数据的学习总结，以及用户可管理的数据生命周期**。

本阶段严格按以下顺序推进：

```text
确定性事件与用户开关
→ 产品埋点与指标口径
→ 每日/每周学习总结
→ 隐私说明、数据导出、删除与账号注销
```

核心原则：

1. 事件由程序判断，模型只负责润色表达。
2. 主动打扰必须由用户明确开启，且随时可以关闭。
3. 指标由程序根据真实记录计算，不能让模型“估算”。
4. 总结只能引用已落库的学习事实，数据不足就明确说不足。
5. 数据导出、删除和注销必须有用户确认、审计和可回滚边界。
6. 没有明确确认前，只做文档评审，不进入业务代码开发。

- 不把学习总结当作医学、心理、教育效果诊断。
- 不在没有可靠通知渠道和用户订阅的情况下发送站外提醒。

## 三、当前基线与技术适配摘要

### 3.1 已有可复用能力

第六阶段已经提供：

- 用户身份、数据库持久化和用户隔离。
- `study_sessions`、`daily_study_records`、`daily_goals` 等学习事实表。
- 会话内记忆、三类受控长期记忆和删除入口。
- Agent Runtime、工具权限、用户确认动作。
- `agent_events` 脱敏轨迹、`requestId` 查询和指标汇总基础。
- 统一时区配置，默认 `Asia/Shanghai`。
- 前端正式页面：陪伴页、专注页、个人页和语音 Provider。

### 3.2 本阶段可能新增的技术影响

P2 将新增或扩展四类数据：

1. **主动陪伴偏好**：是否开启中途鼓励、主动提醒、语音播报等用户设置。
2. **产品事件**：用于统计漏斗和留存的最小化事件元数据。
3. **总结快照**：程序计算的统计事实和模型生成的展示文本之间的绑定关系。
4. **数据管理记录**：导出、删除、注销请求的状态、时间和结果。

本阶段不改变既有 Agent Harness 核心架构，继续沿用“程序决定事实与权限，模型生成表达”的原则。由于涉及新的数据保留、删除和第三方服务披露，真正开发前应复核并更新《后端开发技术适配声明.md》的 P2 实施状态。

### 3.3 不新增外部服务的默认方案

首版采用：

- 站内提醒和聊天页/专注页事件提示。
- 既有 LLM/TTS 适配入口，不新增供应商。
- 产品事件写入现有数据库或同库事件表。
- 导出由后端生成 JSON 文件（必要时打包为 ZIP），通过鉴权接口一次性下载。

如需推送、邮件、短信、ASR 或新的分析平台，必须另行完成供应商、数据流向、密钥、失败降级和隐私评估，不能在本阶段默认接入。

## 四、产品目标与成功标准

### 4.1 用户侧目标

- 用户能明确选择是否接受中途鼓励和主动提醒。
- 专注开始、过半、完成等时点有简短且不打扰的反馈。
- 用户可以查看每日或每周真实学习总结。
- 用户能查看、导出、删除自己的学习数据和记忆，并能发起账号注销。
- 关闭语音或主动提醒后，相关事件不再调用对应服务。

### 4.2 产品侧目标

- 可准确计算每周专注天数、首次完成率、开始到完成转化率、7 日留存等指标。
- 能区分真实模型回复、本地降级回复、语音成功/失败和主动提醒关闭。
- 能根据事件数据判断主动陪伴是否有价值，而不是凭感觉继续增加打扰。

### 4.3 阶段完成的最低标准

1. 主动陪伴触发只来自确定性事件和用户开关。
2. 所有主动提醒都可审计、可关闭、可防重复。
3. 指标口径有程序实现、测试和文档说明。
4. 总结中的数字与数据库事实一致，数据不足不编造。
5. 数据管理接口只作用于当前登录用户，并有二次确认和状态记录。
6. 自动测试、人工主链路、隐私文案和回滚方案齐全。

## 六、P2-01：主动陪伴规则

### 6.1 事件与触发原则

所有触发事件由后端或前端可信状态机产生，不由模型自证：

| 事件 | 触发条件 | 默认行为 | 用户控制 |
|---|---|---|---|
| `focus.started` | 用户确认开始且计时状态成功写入本地 | 站内显示一句确认 | 可关闭语音；文字确认保留 |
| `focus.halfway` | 可信计时达到本轮有效时长的 50% | 默认不主动打扰 | 用户开启“中途鼓励”后才显示/播报 |
| `focus.completed` | 结算接口成功且幂等记录完成 | 显示完成结果和庆祝文案 | 可关闭语音；不得重复结算 |
| `focus.paused_repeated` | 在限定窗口内连续暂停达到阈值 | 仅在用户允许时询问是否缩短时长 | 可关闭，不触发诊断 |
| `study.inactive` | 程序统计发现一段时间无记录 | 首版不自动发送站外提醒 | 用户主动订阅后才允许进入提醒队列 |

### 6.2 频率限制与幂等

- 同一 `sessionId` 的同一事件最多处理一次。
- `focus.halfway` 在刷新、重复轮询或页面重新打开时不得重复发送。
- 同一用户站内主动提醒设置最小冷却窗口，具体数值进入开发前决策表。
- 任何后台触发都必须带 `user_id`、`event_id`、规则版本和触发时间。
- 发送失败不得伪造“已发送”；可记录失败并在用户下一次打开页面时降级显示。
- 主动陪伴失败不能影响番茄结算、统计或用户继续学习。

### 6.3 模型与文案边界

模型只接收已确认的事件类型、用户允许的语气偏好和必要学习上下文；模型不得看到或决定：

- 是否订阅提醒；
- 触发时间和频率；
- 用户 ID、Token、内部指标原始数据；
- 删除、导出、注销或其他高风险动作。

文案必须：

- 简短、具体、非评判；
- 不使用“你必须”“你落后了”等制造压力的表达；
- 不冒充心理、医疗或教育专业结论；
- 生成失败时使用固定本地文案。

### 6.4 推荐数据结构

开发时可在 `user_preferences` 增加字段，或建立独立 `companion_preferences` 表。无论采用哪种方案，至少表达：

```text
mid_session_encouragement_enabled: bool
proactive_reminder_enabled: bool
voice_for_companion_enabled: bool（或复用现有 voice_enabled，但要明确语义）
quiet_hours_start/end: optional local time
reminder_cooldown_minutes: integer
updated_at: datetime
```

不得把“关闭语音”错误解释为“允许文字主动提醒”，也不得把“关闭主动提醒”错误解释为用户拒绝所有站内状态反馈。

## 七、P2-01 前端与接口方案

### 7.1 用户设置入口

推荐放在个人页或设置区域，清楚区分：

- 中途鼓励：专注过半时是否显示/播报。
- 主动提醒：多日未学习时是否允许进入提醒队列。
- 语音：是否使用 TTS；继续复用现有全局语音开关。
- 安静时段：仅影响可选提醒，不影响用户主动打开页面看到的结果。

开关修改应立即保存；保存失败要恢复界面状态并提示，不得显示假成功。

### 7.2 建议接口

| 方法 | 路径 | 用途 | 权限 |
|---|---|---|---|
| GET | `/api/v1/companion/preferences` | 读取当前用户主动陪伴设置 | 登录用户 |
| PUT | `/api/v1/companion/preferences` | 更新白名单设置 | 登录用户 |
| POST | `/api/v1/companion/events/{event_id}/ack` | 确认站内事件已展示（可选） | 当前用户 |
| GET | `/api/v1/companion/inbox` | 读取未展示的站内提醒 | 当前用户 |
| POST | `/api/v1/companion/inbox/{id}/dismiss` | 忽略提醒 | 当前用户 |

接口不得接受任意 `user_id`、任意事件类型或任意发送时间。

## 八、P2-02：产品埋点与指标

### 8.1 事件白名单

事件必须是固定枚举，不接受前端自由拼接事件名。建议首批事件：

```text
auth.registered
auth.login.succeeded
chat.request.started
chat.response.completed
agent.fallback.used
goal.viewed
goal.updated
focus.started
focus.paused
focus.resumed
focus.completed
focus.completion_failed
focus.halfway_shown
companion.reminder_shown
companion.reminder_dismissed
companion.preference_changed
summary.viewed
memory.viewed
memory.changed
data.export.requested
data.export.completed
data.deletion.requested
account.deletion.requested
```

### 8.2 事件字段与隐私

每个事件最少包含：

- `event_id`：唯一事件 ID；
- `user_pseudonym` 或内部用户关联键（查询时仍必须做权限控制）；
- `event_type`；
- `occurred_at`（统一 UTC 存储，展示按用户时区转换）；
- `source`：web、api、agent、system；
- `schema_version`；
- 与事件有关的非敏感数值字段。

禁止写入：密码、Token、邀请码、API Key、完整聊天正文、危机原文、记忆正文、原始 Authorization 头和第三方响应中的敏感字段。

### 8.3 指标口径

| 指标 | 程序定义 |
|---|---|
| 每周专注天数 | 指定用户时区的一周内存在至少一条有效完成记录的日期数 |
| 首次完成专注比例 | 新注册用户中在观察窗口内至少完成一次有效专注的用户数 / 进入观察窗口的用户数 |
| 开始到完成转化率 | 有效 `focus.started` 中最终产生有效 `focus.completed` 的比例；按 session 去重 |
| 7 日留存率 | 注册后第 1～7 天窗口内再次发生有效学习行为的用户比例；具体 cohort 口径需确认 |
| AI 对话后继续学习率 | 完成一次聊天后，在规定时间窗内产生 `focus.started` 或 `focus.completed` 的用户比例 |
| 本地降级比例 | 使用本地回复的合格请求数 / 需要回复的合格请求总数 |
| 主动提醒关闭比例 | 关闭主动提醒的用户数 / 曾打开设置或接收提醒的用户数；分母必须固定记录 |

所有指标应有单元测试、边界样本和一份可复核的 SQL/Repository 查询实现。

### 8.4 保留与查询

- 事件保留周期沿用第六阶段轨迹保留配置，若要改变必须更新技术适配声明。
- 指标查询应优先读取聚合事实，不在请求路径上扫描无限历史。
- 不为 P2 默认建设公开运营后台；首版可使用受限 CLI 或内部查询脚本。
- 任何内部查询也必须去除聊天正文和敏感数据。

## 九、P2-03：每日/每周学习总结

### 9.1 数据事实与表达分层

程序先计算结构化事实：

```json
{
  "period": "2026-09-01/2026-09-07",
  "timezone": "Asia/Shanghai",
  "study_days": 4,
  "completed_sessions": 6,
  "total_minutes": 150,
  "goals_set": 5,
  "goals_completed": 3,
  "streak_at_end": 2,
  "data_quality": "complete"
}
```

模型只负责把这份事实组织成适合用户阅读的文字。它不能自行添加不存在的日期、分钟数、目标完成情况或因果结论。

### 9.2 数据不足与异常

- 没有有效学习记录时，返回“本周期暂无足够记录”，不生成鼓励性虚构数字。
- 记录出现冲突、迁移未完成或数据库不可用时，返回明确的暂不可用提示。
- 统计跨时区展示时以用户配置时区为准，数据库仍保存统一时间格式。
- 总结生成失败时，保留程序计算的数字卡片，文字降级为固定模板。

### 9.3 建议接口

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/v1/summaries/daily?date=YYYY-MM-DD` | 获取某日总结 |
| GET | `/api/v1/summaries/weekly?start=YYYY-MM-DD` | 获取某周总结 |
| POST | `/api/v1/summaries/weekly/generate` | 在用户主动请求时生成或刷新 |

接口返回应区分：

- `facts`：程序计算、可审计的数据；
- `text`：模型或本地模板生成的展示文本；
- `source`：`model` 或 `local_fallback`；
- `generated_at`；
- `data_version` / `rules_version`。

### 9.4 缓存与幂等

- 相同用户、周期、统计规则版本下，重复请求不得重复创建无限总结记录。
- 若允许刷新，必须显式记录刷新原因和版本。
- 总结不应成为新的事实来源；学习记录变化后应能重新计算。
- 删除学习数据后，相关总结缓存必须失效或被删除。

## 十、P2-04：隐私说明与用户数据管理

### 10.1 必须披露的数据流

产品文档和页面至少说明：

- 用户文字是否发送给所选 LLM 服务；
- 浏览器语音识别是否经过浏览器/系统服务；
- TTS 文本是否发送给语音服务；
- 保存哪些聊天、学习记录、记忆和轨迹元数据；
- 各类数据的保存期限；
- 如何查看、更正、导出、删除和注销；
- 关闭语音或主动提醒后，哪些请求不会再发生。

说明必须与真实实现一致，不能继续使用“所有内容只在本机”“完全不外传”等绝对表述。

### 10.2 数据分类

| 数据类 | 示例 | 默认保留 | 用户操作 |
|---|---|---|---|
| 账号数据 | 用户名、密码哈希、会话摘要 | 账号存续期间 | 注销时删除或按法律要求保留最小记录 |
| 学习事实 | 目标、完成记录、每日统计 | 账号存续期间 | 查看、导出、删除 |
| 聊天数据 | 会话、消息、摘要 | 沿用 P1-C 规则 | 查看、删除、导出 |
| 长期记忆 | 三类白名单记忆 | 用户明确保存期间 | 查看、修改、删除 |
| 轨迹/埋点 | 脱敏事件、指标 | 配置的保留周期 | 按规则清理，不导出敏感内部字段 |
| 导出任务 | 请求状态、文件元数据 | 短期 | 查看状态、过期自动清理 |

### 10.3 导出流程

推荐流程：

```text
用户发起导出
→ 要求当前登录态 + 一次性确认
→ 创建 pending 任务
→ 后台或受限同步生成 JSON/ZIP
→ 用户下载一次
→ 文件到期清理并记录完成状态
```

导出内容应包含用户自己的账号基本信息、学习目标/记录、聊天、长期记忆和可向用户解释的总结；不应包含内部密钥、Token、其他用户数据、完整内部轨迹 payload 或供应商凭证。

### 10.4 删除与注销流程

- 删除聊天、记忆、学习数据和账号注销必须分别定义范围，不允许一个模糊按钮删除全部数据。
- 账号注销属于高风险、不可逆操作，必须二次确认、再次输入明确短语或使用一次性确认凭证。
- 注销前应允许用户导出数据；注销后撤销所有会话 Token。
- 删除任务应幂等，重复请求返回当前状态，不重复执行。
- 失败时不得显示已删除；应返回“处理中/失败，请稍后重试”。
- 需要保留的安全审计记录只能保留最小化、脱敏元数据，并在隐私说明中说明。

可以新增 `data_subject_requests`：

## 十三、测试计划

### 13.1 主动陪伴规则测试

- 事件触发条件、边界时间和时区转换。
- 同一 `sessionId` 事件幂等。
- 刷新、重连、重复轮询不重复提醒。
- 关闭中途鼓励、语音和主动提醒后的行为。
- 安静时段和频率限制。
- LLM/TTS 失败时不影响学习事实写入。
- 危机输入不会触发普通主动陪伴。

### 13.2 埋点与指标测试

- 未注册事件拒绝。
- 事件字段脱敏和用户隔离。
- 每周专注天数、首次完成率、转化率、留存率的边界样本。
- 重复事件不会重复计数。
- 统计时间窗和用户时区正确。
- 轨迹/埋点写入失败不回滚业务事实，但要产生可观察错误。

### 13.3 总结测试

- 总结数字与数据库事实逐项相等。
- 空数据、部分数据、冲突数据和数据库不可用时不编造。
- 模型输出含不存在数字时被拒绝或改用模板。
- 重复生成具有幂等或明确版本行为。
- 删除学习记录后总结缓存失效。

### 13.4 数据权利测试

- 导出只能包含当前用户数据。
- 导出文件不含密码、Token、邀请码、API Key 和危机原文。
- 导出任务过期自动清理，下载权限失效。
- 删除/注销必须确认，重复请求幂等，失败不假成功。
- 注销立即撤销 Token，并阻止继续访问受保护 API。
- 删除后会话、记忆、目标、统计、轨迹和总结的关系符合声明。
- 并发删除与正常写入有明确事务边界。

### 13.5 前端和 E2E

- 开关保存、刷新恢复和跨页面一致。
- 专注开始/过半/完成提示展示正确。
- 总结页面的事实和文本分区可理解。
- 导出、删除、注销有清晰范围和二次确认。
- 双账号隔离、退出登录、过期 Token 无回归。
- 无 hydration mismatch；无关闭语音后 TTS 请求。

### 13.6 统一验证

```bash
./scripts/verify.sh
```

自动测试必须继续使用临时 SQLite、匿名测试账号、假模型和 TTS 拦截；不得连接生产数据库或发送真实用户数据。

## 十四、真实服务与人工验收

### 14.1 真实模型冒烟

只有在自动测试通过并获得单独明确许可后，才能在隔离测试账号中执行。必须记录：模型、端点、规则版本、样例类型、降级结果和费用/时延观察。不能把这一步混入普通自动测试。

### 14.2 人工产品验收

按以下顺序：

1. 新账号登录并检查主动陪伴默认设置。
2. 分别开启/关闭中途鼓励、主动提醒和语音。
3. 启动一轮短测试专注，验证开始、过半、完成事件不重复。
4. 查看每日/每周总结，逐项核对真实分钟数和专注天数。
5. 发起导出，下载并检查内容范围与敏感字段。
6. 删除一类记忆或聊天，确认页面与 Agent 上下文同步变化。
7. 以隔离账号演练注销，确认 Token 撤销和数据处理结果。
8. 检查危机文本不会触发普通提醒和运营总结。

### 14.3 发布门槛

在以下项目全部完成前不得正式扩大用户范围：

- P0-C PostgreSQL 隔离实库验收。
- P1-B/P1-C 人工主链路和安全复核。
- P2 主动陪伴、指标、总结和数据管理 E2E。
- 隐私说明、数据保留和删除策略与实现一致。
- 真实模型/TTS 冒烟（如产品决定启用真实服务）。
- 生产密钥、备份、恢复和部署配置复核。

## 十五、风险、停止条件与回滚

| 风险/停止条件 | 处理方式 |
|---|---|
| 主动提醒造成明显打扰或投诉 | 立即关闭规则触发，保留用户主动查看；不依赖模型自行调频 |
| 指标口径无法由真实数据复算 | 暂停对外展示指标，先修正事实层和测试 |
| 总结出现虚构数字 | 禁止发布文本总结，暂时只展示程序事实卡片 |
| 删除范围不清或无法恢复 | 停止开放删除/注销入口，先补齐数据分类、备份和幂等设计 |
| 外部推送服务不稳定 | 回退到站内提醒，不丢失学习事实 |
| PostgreSQL 与 SQLite 行为不一致 | 停止迁移/发布，补隔离实库测试 |
| 发现敏感数据进入事件或导出 | 立即停止相关写入/下载，清理受影响数据并记录事故 |

任何数据删除、账号注销和第三方触达都必须可追踪；不能使用不可逆的批量命令作为首次实现方式。
