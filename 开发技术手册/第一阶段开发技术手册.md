## 一、阶段说明

### 1.1 本手册中的“第一阶段”是什么

根据《AI 学习搭子开发排期手册》，本手册将第一阶段定义为：

> P0-A：建立可信开发基线。

本阶段不开发 Agent 循环、长期记忆、数据库或新产品功能，主要解决三个基础问题：

1. 项目中存在三代前端，需要明确唯一正式版本。
2. 配置模板缺少登录和安全相关配置，新环境无法直接使用。
3. 自动测试入口不统一，端到端测试仍依赖旧邀请码。

只有本阶段完成，后续统计修复、数据迁移和 Agent Harness 开发才有稳定基础。

### 1.2 阶段目标

完成后，项目应达到以下状态：

- `frontend/` 是唯一正式前端。
- `backend/` 是唯一正式后端。
- 旧版 H5 和历史 PRD 已明确归档，不再参与正式构建与测试。
- 新开发者复制 `.env.example` 后可以按 README 启动项目。
- 测试环境不依赖真实邀请码、真实数据和开发者本地配置。
- 后端测试、前端 lint、生产构建和 E2E 可以通过统一入口执行。
- README、配置说明、启动方式和实际代码一致。

### 1.3 本阶段不做什么

- 不修复连续天数和本周专注天数算法。
- 不修改番茄钟恢复和结算逻辑。
- 不迁移数据库。
- 不重做账号系统。
- 不增加 Agent 循环、工具系统或记忆系统。
- 不增加周报、成就、提醒和数字人功能。
- 不改变现有产品视觉设计。

以上内容分别属于后续 P0-B、P0-C、P1 和 P2 阶段。

## 五、P0-A01：明确唯一正式版本

### 5.1 目标

让所有人清楚知道：

- 用户应访问 Next.js 前端，而不是后端内嵌旧 H5。
- 前端和后端应分别启动、分别部署。
- 历史原型只用于查阅，不再作为正式产品入口。

### 5.2 文件处理清单

| 当前路径 | 目标路径 | 处理方式 |
|---|---|---|
| `study-buddy/` | `archive/single-file-prototype/` | 整体移动 |
| `study-buddy.md` | `archive/product-docs/study-buddy.md` | 移动并标记历史版本 |
| `backend/app/static/` | `archive/backend-static-h5/` | 移动旧 H5 和旧资源 |
| `frontend/` | 原位置 | 保持正式前端 |
| `backend/` | 原位置 | 保持正式后端 |

移动前必须确认：

- `frontend/public/assets/buddy-male.jpg` 存在。
- `frontend/public/assets/buddy-female.jpg` 存在。
- 正式前端没有引用 `backend/app/static/` 中的文件路径。
- 旧版 H5 没有被当前部署脚本当作正式入口。

### 5.3 调整 FastAPI 根入口

当前 `backend/app/main.py` 会把 `backend/app/static/` 挂载到 `/`。旧 H5 归档后，应删除该静态页面挂载逻辑。

推荐将后端根入口调整为服务信息或健康检查，不再返回产品页面：

```text
GET /health
返回：服务状态、应用名称和版本
```

最低返回示例：

```json
{
  "status": "ok",
  "service": "study-buddy-api"
}
```

注意：

- 健康检查不能返回密钥、数据库地址、邀请码和内部路径。
- API 前缀继续保持 `/api/v1`，避免影响正式前端。
- 部署平台如果正在使用 `/` 作为健康检查，应先改为 `/health`，再移除静态挂载。

### 5.4 调整后端测试

当前后端测试中存在“访问 `/` 返回旧 H5”的检查。归档旧 H5 后，应将它替换为健康检查测试。

需要验证：

- `GET /health` 返回 200。
- 响应包含 `status=ok`。
- `/api/v1/*` 接口行为不变。
- 旧 H5 路径不再被当作正式产品入口。

### 5.5 更新归档说明

两个归档目录都应有简短 README，至少写明：

- 这是哪个阶段的版本。
- 为什么已经停止使用。
- 当前正式版本在哪里。
- 禁止从该目录执行正式部署。

示例说明：

```markdown
# 历史版本说明

本目录保存 AI 学习搭子的早期 H5 原型，仅用于查看产品演进过程。
当前正式前端位于项目根目录的 `frontend/`，请勿从本目录部署。
```

### 5.6 P0-A01 验收标准

- 项目根目录只将 `frontend/` 标记为正式前端。
- 后端不再提供旧产品页面。
- `/health` 可以用于后端存活检查。
- 正式前端图片和页面显示正常。
- 历史文件已归档且没有被删除。
- 后端 API 测试没有因为归档而失效。
- 项目文档中的旧路径已经同步更新。

## 六、P0-A02：修复配置模板和启动校验

### 6.1 目标

解决“复制 `.env.example` 后仍然无法登录”和“生产环境可能误用默认密钥”的问题。

### 6.2 配置分类

建议把配置分为四类：

| 类别 | 配置项 | 是否必填 |
|---|---|---|
| 运行环境 | `APP_ENV`、`APP_TIMEZONE` | 是 |
| 模型 | `LLM_BASE_URL`、`LLM_API_KEY`、`LLM_MODEL`、模型参数 | Key 可选 |
| 登录 | `INVITE_CODES`、`AUTH_SECRET` | 当前版本必填 |
| 数据 | `DATA_DIR`、预留 `DATABASE_URL` | 当前使用 `DATA_DIR` |

### 6.3 `.env.example` 建议内容

示例文件不得包含任何真实生产值。建议结构如下：

```dotenv
# 运行环境：development / test / production
APP_ENV=development
APP_TIMEZONE=Asia/Shanghai

# 大模型；LLM_API_KEY 留空时使用本地话术
LLM_BASE_URL=https://open.bigmodel.cn/api/paas/v4
LLM_API_KEY=
LLM_MODEL=glm-4-flash
LLM_TEMPERATURE=0.8
LLM_MAX_TOKENS=300

# 本地开发邀请码；生产环境必须在平台环境变量中设置
INVITE_CODES=DEMO123

# 仅为格式示例；本地和生产都应替换为随机长字符串
AUTH_SECRET=replace-with-a-long-random-secret

# 当前 JSON 数据目录
DATA_DIR=./data

# P0-C 数据库阶段启用，第一阶段只保留说明
# DATABASE_URL=sqlite:///./data/study_buddy.db
```

### 6.4 后端配置对象调整

`backend/app/core/config.py` 需要增加：

- `app_env`
- `app_timezone`
- 对 `AUTH_SECRET` 的启动校验
- 对模型温度、最大 Token 等数字配置的合法性检查
- 统一的配置错误提示

建议校验规则：

| 配置 | 开发环境 | 测试环境 | 生产环境 |
|---|---|---|---|
| `LLM_API_KEY` 为空 | 允许，使用本地话术 | 允许且默认为空 | 允许，但应记录降级状态 |
| `INVITE_CODES` 为空 | 启动时明确提示无法登录 | 不允许 | 不允许 |
| `AUTH_SECRET` 为示例值或默认值 | 警告 | 测试专用值 | 拒绝启动 |
| 时区无法识别 | 拒绝启动 | 拒绝启动 | 拒绝启动 |

### 6.5 密钥和邀请码处理规则

- `.env` 必须继续被 Git 忽略。
- `.env.example` 只能包含假值。
- 生产邀请码只能放在部署平台环境变量中。
- README 不再公开生产邀请码。
- 日志不能打印 `AUTH_SECRET`、`LLM_API_KEY`、Token 或完整邀请码。
- 配置校验失败时，只说明缺少哪个配置，不回显配置值。

### 6.6 增加配置测试

至少增加以下测试：

- 开发环境无模型 Key 时可以启动。
- 测试环境使用测试邀请码可以登录。
- 生产环境使用默认或示例 `AUTH_SECRET` 时拒绝启动。
- `INVITE_CODES` 为空时给出明确错误。
- 温度、最大 Token 和时区格式错误时给出明确错误。
- 错误信息中不包含密钥内容。

### 6.7 P0-A02 验收标准

- 新环境复制 `.env.example` 后可以启动和登录。
- 不配置模型 Key 时，本地话术可正常工作。
- 生产环境不能使用默认签名密钥。
- 生产邀请码不出现在 README、源码和测试文件中。
- 配置错误能够在启动阶段发现，而不是用户请求后才报错。
- 日志和错误响应不泄露敏感配置。

## 七、P0-A03：建立统一测试入口

### 7.1 目标

建立一个开发人员和发布流程都能使用的统一验证入口，解决以下问题：

- 后端、前端和 E2E 需要分别手动执行。
- E2E 依赖开发者本地邀请码。
- 测试可能写入真实 `backend/data/`。
- 默认生产构建在当前环境受 Turbopack 影响。

### 7.2 测试分层

| 检查层 | 命令或入口 | 目的 |
|---|---|---|
| 后端单元与接口测试 | `backend/.venv/bin/python -m pytest -q` | 验证 API 和服务逻辑 |
| 前端静态检查 | `npm run lint` | 发现前端代码规范问题 |
| 前端生产构建 | `npm run build -- --webpack` | 验证正式构建可完成 |
| 浏览器端到端测试 | `npm run test:e2e` | 验证真实用户闭环 |
| 统一入口 | `scripts/verify.sh` | 按顺序运行以上检查 |

### 7.3 增加 `scripts/verify.sh`

脚本应具备以下行为：

1. 自动定位项目根目录，不依赖开发者当前所在目录。
2. 检查后端虚拟环境和前端依赖是否存在。
3. 依次运行后端测试、前端 lint、webpack 构建和 E2E。
4. 任意一步失败时立即停止，并返回非零退出码。
5. 输出清晰的当前步骤和最终结果。
6. 不自动修改真实 `.env`。
7. 不调用真实 LLM 和真实 TTS 服务。

推荐执行顺序：

```text
后端 pytest
→ 前端 lint
→ 前端 webpack build
→ Playwright E2E
```

### 7.4 增加 `scripts/run-e2e.sh`

E2E 包装脚本应：

- 使用 `mktemp -d` 创建临时数据目录。
- 设置测试专用 `INVITE_CODES=DEMO123`。
- 设置测试专用 `AUTH_SECRET`。
- 强制清空 `LLM_API_KEY`，避免产生真实模型费用和不稳定网络请求。
- 将 `DATA_DIR` 指向临时目录。
- 测试结束后清理临时目录和本地服务。
- 无论测试成功还是失败，都执行清理步骤。

建议的测试环境变量：

```text
APP_ENV=test
APP_TIMEZONE=Asia/Shanghai
INVITE_CODES=DEMO123
AUTH_SECRET=e2e-only-secret-not-for-production
LLM_API_KEY=
DATA_DIR=<临时目录>
```

这些值只能用于本地自动测试，不能用于正式部署。

### 7.5 调整 Playwright 配置

`frontend/playwright.config.ts` 应满足：

- 后端服务读取测试脚本提供的环境变量。
- 前端继续通过 `http://localhost:3000` 访问。
- 前端 API 继续转发到测试后端 `http://localhost:8000`。
- 测试不读取生产邀请码。
- 测试失败时保留错误上下文、截图或 trace，成功后不保留大量产物。
- 后端健康检查使用 `/health`，不再使用需要登录的 `/api/v1/stats`。

### 7.6 修复 E2E 用例

保留并修复以下三条现有用例：

1. 已登录核心闭环：聊天 → 专注 → 我的。
2. 未登录访问首页跳转登录页。
3. 错误邀请码被拒绝。

增加以下基线用例：

4. 正确测试邀请码可以登录。
5. 无效或过期 Token 会返回登录页。
6. 退出登录后不能继续访问受保护页面。
7. 关闭语音时进入专注页不会自动播放语音。

注意：本阶段只建立测试基线。统计跨天和番茄钟补结算等业务测试在 P0-B 阶段增加。

### 7.7 测试数据隔离

必须确保：

- pytest 使用自己的临时目录。
- Playwright 使用自己的临时目录。
- 测试不能读写 `backend/data/` 中的真实用户数据。
- 测试不能调用真实大模型。
- 测试不能依赖开发者已经登录的浏览器状态。
- 每条浏览器测试使用独立上下文或主动清理 localStorage。

### 7.8 P0-A03 验收标准

- 执行统一验证脚本后，全部检查通过。
- Playwright 不依赖真实 `.env` 和生产邀请码。
- 测试前后真实数据目录内容没有变化。
- 测试过程没有调用真实 LLM。
- 构建命令稳定使用 webpack。
- 错误发生时，脚本能指出失败环节并返回失败状态。

## 十、开发过程中的安全规则

- 不读取、打印或提交真实 `.env` 内容。
- 不把生产邀请码复制到测试代码。
- 不直接删除历史版本，先移动到归档。
- 不删除或覆盖 `backend/data/` 中的用户数据。
- 不在本阶段执行数据库迁移。
- 不在自动测试中调用真实 LLM、TTS 或生产接口。
- 移动文件前检查是否存在前端引用、部署引用和文档链接。
- 修改部署健康检查前，先确认线上平台使用的路径。
- 如果发现当前部署仍依赖旧静态 H5，应暂停归档动作并先调整部署配置。

## 十一、风险和回退方案

| 风险 | 预防措施 | 回退方式 |
|---|---|---|
| 移走 `backend/app/static/` 后后端根路径失效 | 先增加 `/health`，再调整部署健康检查 | 恢复静态挂载并重新部署 |
| 文档或代码仍引用旧路径 | 移动前后全局搜索旧路径 | 将文件移回原位置并修复链接 |
| E2E 启动不了后端 | 使用独立脚本注入测试配置 | 恢复原 Playwright 启动命令 |
| 测试误写真实数据 | 强制 `DATA_DIR` 指向临时目录 | 停止测试并从备份恢复数据 |
| webpack 与部署命令不一致 | 在 package script 和部署配置中使用同一命令 | 恢复已验证的旧构建命令 |
| 配置校验导致线上启动失败 | 部署前检查平台环境变量 | 回滚校验改动并补齐环境变量后再发布 |

所有回退都应通过版本控制完成，不使用直接覆盖或不可恢复的删除操作。

## 十三、人工验收流程

按照以下顺序完成一次人工验收：

1. 使用一份不包含真实密钥的测试配置启动后端。
2. 访问 `/health`，确认后端正常。
3. 启动正式 Next.js 前端。
4. 打开 `http://localhost:3000`。
5. 使用测试邀请码登录。
6. 确认可以进入陪伴页。
7. 发送一条聊天消息，确认本地话术能够回复。
8. 切换到专注页并启动番茄钟。
9. 切换到“我的”页面，确认页面正常加载。
10. 退出登录，确认返回登录页。
11. 执行统一验证脚本，确认全部检查通过。
12. 检查真实数据目录未被测试修改。
