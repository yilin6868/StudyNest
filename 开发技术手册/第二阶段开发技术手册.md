## 一、先说简单结论

第二阶段不增加新功能，也不开始建设 Agent Harness。

这一阶段只修复四件事：

1. 让“连续学习几天、本周学习几天”算得准确。
2. 让番茄钟刷新或关闭页面后不漏记、不重复记。
3. 让所有页面真正共用同一个语音开关。
4. 让登录、登录过期和退出登录的页面状态正确。

可以把这一阶段理解为：

```text
先把现有产品中的账算准、计时存准、语音关得住、登录管得住
→ 再进入数据库和账号体系改造
→ 最后才建设 Agent Harness
```

## 五、当前问题与目标方案对照

| 问题 | 当前表现 | 本阶段目标 | 主要位置 |
|---|---|---|---|
| 长期统计不准 | `stats.json` 自己维护 streak 和 weekDays，跨天容易丢失 | 从 `history.json` 的每日记录实时计算 | 后端统计与历史服务 |
| 时区不统一 | 使用服务器本地时间 | 统一使用 `APP_TIMEZONE` | 后端时间工具 |

| 番茄重复记 | 完成接口没有唯一编号 | `sessionId` 幂等记账 | 后端完成接口 |
| 假成功 | 后端失败时前端仍给番茄数加一 | 保留失败状态并显示重试 | 正式前端专注页 |
| 语音不一致 | 专注页不读取陪伴页的语音开关 | 使用全局语音状态 | 前端 Provider 与两页面 |
| 旧语音继续播放 | 关闭开关后旧请求仍可能返回并播放 | 中止请求、忽略过期结果、释放音频 | 前端统一语音控制器 |
| 登录页面闪现 | 只检查本地是否存在 Token | 先请求后端确认，再显示页面 | `AuthGate` 与会话接口 |
| 无退出入口 | 用户无法主动清除登录状态 | “我的”页增加退出登录 | 正式前端 |
| hydration 提示 | 服务端和浏览器首次渲染结构不同 | 浏览器状态在挂载后读取 | 首页和专注页 |

## 六、目标数据关系

第二阶段仍使用 JSON，不提前换数据库，但要减少“同一事实写两份”的问题。

推荐关系：

```text
history.json（本阶段的学习事实来源）
  ├─ days：每天完成了几个番茄、多少分钟
  └─ completedSessions：哪些 sessionId 已经结算
           ↓
StatsService 根据 history.json 计算
  ├─ 今日番茄数
  ├─ 今日分钟数
  ├─ 连续学习天数
  └─ 本周专注日期
```

`stats.json` 不再作为长期统计的可信来源，也不继续写入新统计。为了回滚和后续 P0-C 数据核对，本阶段不能删除旧 `stats.json`。

### 6.1 `history.json` 兼容结构

建议将历史结构升级为版本 2：

```json
{
  "schemaVersion": 2,
  "days": {
    "2026-09-08": {
      "tomato": 2,
      "minutes": 50
    }
  },
  "completedSessions": {
    "0f6f75ce-7d67-46e4-97b4-6bdf963f8495": {
      "date": "2026-09-08",
      "minutes": 25,
      "completedAt": "2026-09-08T21:30:00+08:00"
    }
  }
}
```

兼容规则：

- 旧数据没有 `completedSessions` 时，自动补成空对象。
- 旧的 `days` 内容继续可读，不要求用户重新开始。
- 结构升级只能增加兼容字段，不能删除旧历史记录。
- 读取到错误字段时安全回退，不能覆盖原文件后再报错。
- 开发和测试只能使用复制的匿名样本或临时数据，不能直接试改真实文件。

## 八、P0-B01：修复学习统计

### 8.1 目标

统计只根据真实的每日历史计算，不再依赖容易跨天失真的快照字段。

### 8.2 时间处理

建议新增统一时间工具，例如：

```text
backend/app/core/time.py
```

它只负责：

- 读取 `settings.app_timezone`。
- 使用 Python `zoneinfo.ZoneInfo` 创建时区。
- 返回当前本地日期和带时区的当前时间。
- 允许测试传入固定日期，避免测试依赖电脑当天时间。

禁止继续直接使用没有时区的：

```python
datetime.now()
date.today()
```

### 8.3 统计计算规则

建议把计算写成纯函数：输入每日历史和“今天是哪天”，输出统计结果。纯函数不直接读写文件，更容易测试。

规则如下：

1. 今日番茄数和分钟数读取 `days[今天]`，没有记录就是 0。
2. 本周从周一开始，到周日结束。
3. 本周专注天数只统计当前周内 `tomato > 0` 的日期。
4. 连续天数按每天是否至少完成一次专注判断。
5. 如果今天已经完成，从今天向前连续计算。
6. 如果今天还未完成，可以从昨天向前计算，避免用户上午打开时连续记录提前归零。
7. 中间任何一天没有完成，连续计算立即停止。
8. 未来日期、格式错误日期和负数数据不进入统计。

### 8.4 服务调整

建议职责变为：

| 服务 | 调整后职责 |
|---|---|
| `HistoryService` | 保存和读取每日学习事实、幂等 session 记录 |
| `StatsService` | 读取 HistoryService 的结果并计算展示统计 |
| `JsonStore` | 提供安全的原子读写或同文件更新能力 |

`GET /api/v1/stats` 的响应结构保持不变，避免正式前端和部署中的旧版本突然失效：

```json
{
  "date": "2026-09-08",
  "tomato": 2,
  "minutes": 50,
  "streak": 3,
  "weekDays": ["2026-09-07", "2026-09-08"]
}
```

### 8.5 后端测试

至少增加以下测试：

- 今天没有学习时，今日统计为 0。
- 连续三天学习时 streak 为 3。
- 今天还没完成、昨天及前天连续完成时，streak 保持 2。
- 中断一天后今天完成，streak 为 1。
- 同一周两天有记录，weekDays 只有两天。
- 上周记录不进入本周。
- 周日到下周一切换正确。
- `Asia/Shanghai` 跨零点时日期正确。
- 损坏日期、负数和非数字字段不会把接口弄崩。
- 两个用户的历史和统计仍然隔离。

### 8.6 验收标准

- [ ] 连续三天完成学习，连续天数显示 3。
- [ ] 同一周两天完成学习，本周专注显示 2 天。
- [ ] 中断一天后重新学习，连续天数从 1 开始。
- [ ] 跨周后只统计新一周。
- [ ] 今日番茄和分钟数与历史记录一致。
- [ ] API 返回结构没有破坏现有前端。

## 九、P0-B02：修复番茄钟恢复与结算

### 9.1 目标

无论用户刷新页面、关闭页面、网络失败或重复点击，同一轮专注最终只能出现两种可信结果：

```text
没有结算
或
成功结算一次
```

不能出现“页面说成功但后端没保存”，也不能出现“同一轮被算两次”。

### 9.2 前端计时状态

建议将 `sb_timer` 升级为带版本号的结构：

```json
{
  "schemaVersion": 2,
  "sessionId": "0f6f75ce-7d67-46e4-97b4-6bdf963f8495",
  "mode": "focus",
  "status": "running",
  "startedAt": 1788872400000,
  "endAt": 1788873900000,
  "remainingSeconds": 1500
}
```

状态只允许：

| 状态 | 含义 |
|---|---|
| `idle` | 尚未开始 |
| `running` | 正在倒计时 |
| `paused` | 用户已暂停 |
| `pending_settlement` | 时间已结束，等待后端确认 |
| `settlement_failed` | 后端保存失败，可重试 |
| `settled` | 本轮已经成功结算 |

### 9.3 `sessionId` 规则

- 每次开始一轮新的专注时生成一个 UUID。
- 暂停和继续使用同一个 `sessionId`。
- 刷新或重新打开页面仍使用原来的 `sessionId`。
- 完成或主动重置后，下一轮必须生成新的 `sessionId`。
- 休息计时不调用专注结算接口。
- 不能用当前时间或 `Math.random()` 单独充当唯一编号。
- 优先使用浏览器 `crypto.randomUUID()`；不支持时使用安全随机字节生成兼容 UUID。

### 9.4 页面恢复规则

读取本地计时状态后：

```text
running 且 endAt 在未来
→ 按 endAt 重新计算剩余时间并继续

running 且 endAt 已过去
→ 改为 pending_settlement
→ 使用原 sessionId 调后端补结算

paused
→ 显示保存的 remainingSeconds，不自动运行

settlement_failed
→ 不增加页面统计，显示“保存失败，点击重试”

旧版计时数据没有 sessionId
→ 不自动补记，安全重置并提示重新开始
```

旧版记录不能自动补结算，因为系统无法证明它以前是否已经记过账。

### 9.5 完成接口

继续沿用现有路径：

```text
POST /api/v1/stats/complete
```

请求调整为：

```json
{
  "sessionId": "0f6f75ce-7d67-46e4-97b4-6bdf963f8495",
  "minutes": 25
}
```

要求：

- `sessionId` 必填，并通过 UUID 格式校验。
- `minutes` 继续限制在合理范围内。
- 用户 A 和用户 B 可以各自拥有同名 session，但数据仍按用户隔离。
- 同一用户重复提交同一 session 时返回 200 和当前统计，不再次增加。
- 首次成功时，在一次 `history.json` 原子更新中同时记录 day 和 completedSessions。
- 记录失败时不返回成功。
- 响应继续使用现有 `StatsResponse`，减少前后端发布风险。

### 9.6 JSON 并发边界

本阶段仍未进入数据库阶段。可以在 `JsonStore` 增加“同一进程内的锁 + 原子更新”能力，防止同一服务进程中的两个请求同时改写同一个文件。

必须明确：JSON 文件无法可靠支持多个云端实例同时写入。多实例事务和数据库级唯一约束将在 P0-C 完成。因此第二阶段可以修复当前单实例的重复结算，但不能把它宣传成已经具备数据库级并发保障。

### 9.7 前端失败处理

结算请求成功前：

- 不增加番茄数。
- 不增加累计时间。
- 不切换成“已成功”状态。

请求失败时显示：

```text
本次专注保存失败
[重新保存]
```

点击重试时必须继续使用原 `sessionId`。成功后才刷新统计并进入休息状态。

### 9.8 发布兼容顺序

前后端独立部署时必须按以下顺序：

```text
先发布会发送 sessionId 的前端
→ 验证旧后端仍能接受额外字段
→ 再发布要求 sessionId 的后端
→ 完成接口和 E2E 验证
```

如果无法保证这个顺序，应先让后端短期兼容缺少 `sessionId` 的旧前端，再在确认所有前端升级后收紧为必填。兼容期必须写入验收记录，不能永久保留无幂等编号的入口。

### 9.9 自动测试

至少增加：

- 首次提交 session 统计增加一次。
- 同一 session 连续提交两次只增加一次。
- 同一 session 多次刷新页面只增加一次。
- 同一 session 使用不同 minutes 重试仍不重复记账。
- 两个用户使用相同 sessionId 时各自正常记账。
- 非法 sessionId 返回 422。
- 运行中刷新后剩余时间正确。
- 页面关闭期间超时，再打开后自动补结算一次。
- 第一次保存返回 500 时页面显示重试，不增加统计。
- 重试成功后错误提示消失，统计增加一次。

### 9.10 验收标准

- [ ] 运行中刷新页面，剩余时间正确。
- [ ] 关闭页面超过结束时间后再打开，只补记一次。
- [ ] 连续刷新不会重复增加番茄数。
- [ ] 后端失败时页面明确显示失败和重试入口。
- [ ] 保存失败时页面不会临时增加假数据。
- [ ] 休息计时不会被误记成专注完成。

## 十、P0-B03：统一语音设置

### 10.1 目标

用户关闭语音后，陪伴页和专注页都保持安静；文字、字幕和聊天仍然正常。

### 10.2 推荐前端结构

建议新增一个全局语音 Provider，例如：

```text
frontend/src/components/providers/VoiceProvider.tsx
```

Provider 统一管理：

- `voiceEnabled`：语音是否开启。
- 从 `localStorage` 读取和保存 `sb_voice`。
- 当前 TTS 请求的 `AbortController`。
- 当前正在播放的 `Audio`。
- 当前语音请求编号，防止旧回复晚到后播放。
- Object URL 的创建和释放。
- `speak()`、`stop()` 和 `setVoiceEnabled()`。

陪伴页与专注页都不能再自己直接创建不受控制的 TTS 播放流程。

### 10.3 关闭语音规则

关闭语音时立即执行：

1. 中止尚未完成的 TTS fetch。
2. 增加请求版本号，让已经返回的旧结果失效。
3. 暂停当前 Audio。
4. 释放已经创建的 Object URL。
5. 保留文字和字幕，不影响文字聊天。

`api.tts()` 需要允许传入 `AbortSignal`。Abort 属于正常取消，不显示成“系统故障”。

### 10.4 麦克风状态

- 麦克风能力只能在浏览器挂载后检测，不能在服务端首次渲染时决定页面结构。
- 浏览器不支持 Web Speech API 时，显示“当前浏览器不支持语音输入，请使用文字输入”。
- 用户拒绝麦克风权限时，显示“麦克风权限未开启，可以继续打字”。
- 麦克风不可用不能隐藏文字输入框，也不能阻止发送文字。
- 离开页面时停止语音识别和音频播放。

### 10.5 hydration 修复

以下浏览器专属数据都应在组件挂载后读取：

- 麦克风是否支持。
- `sb_voice`。
- `sb_buddy`。
- `sb_timer`。

服务端和浏览器的第一次渲染使用同一个安全默认值，然后在 `useEffect` 中恢复本地状态，避免第一阶段验收中发现的 hydration mismatch。

### 10.6 自动测试

至少增加：

- 陪伴页关闭语音后不请求 TTS。
- 专注页关闭语音后不请求 TTS。
- 语音在陪伴页关闭，切换到专注页后仍保持关闭。
- TTS 请求未完成时关闭语音，请求被取消且不会播放。
- 快速产生两条回复时，只允许最新语音播放。
- 离开页面时音频和 Object URL 被释放。
- 模拟无麦克风环境时，文字输入和发送仍可用。
- 浏览器控制台不再出现 hydration mismatch。

自动测试仍然只能拦截或模拟 TTS，不能调用真实外部语音服务。

### 10.7 验收标准

- [ ] 关闭语音后任何页面都不播放语音。
- [ ] 页面切换后语音开关状态保持一致。
- [ ] 旧语音响应不会盖过新回复。
- [ ] 麦克风不可用时有清楚提示。
- [ ] 文字聊天始终可用。
- [ ] 浏览器控制台没有 hydration mismatch。

## 十一、P0-B04：修复登录页面状态

### 11.1 目标

本地有一串 Token 不等于已经登录。正式页面必须先让后端确认 Token 有效，再显示用户内容。

### 11.2 新增会话校验接口

建议新增：

```text
GET /api/v1/auth/session
```

有效 Token 返回：

```json
{
  "authenticated": true,
  "userId": "当前用户编号"
}
```

无效或过期 Token 继续返回统一 401 错误。响应不能包含邀请码、Token、签名密钥或用户数据目录。

本阶段不增加数据库和服务端撤销表。主动退出仅清除浏览器中的 Token；服务端撤销能力留到 P0-C。

### 11.3 前端登录状态

`AuthGate` 建议使用三个明确状态：

| 状态 | 页面表现 |
|---|---|
| `checking` | 只显示中性加载画面，不显示受保护页面和底部导航 |
| `authenticated` | 显示正式页面和底部导航 |
| `unauthenticated` | 清除无效 Token 并跳转 `/login` |

受保护页面进入流程：

```text
没有本地 Token
→ 直接进入 unauthenticated
→ 跳转登录页

存在本地 Token
→ 请求 /api/v1/auth/session
→ 200：显示页面
→ 401：清除 Token，跳转登录页
→ 网络错误：显示“暂时无法确认登录状态”和重试入口
```

网络错误不能直接当作 Token 无效，避免短暂断网把用户误退出。

### 11.4 退出登录

建议在“我的”页面增加清楚的“退出登录”按钮。

点击后：

1. 停止当前语音和麦克风。
2. 清除 `sb_token`。
3. 清除仅属于当前会话的临时页面状态。
4. 跳转 `/login`。
5. 再访问受保护页面时必须重新登录。

本阶段不删除学习历史、搭子偏好或番茄记录。退出登录不等于删除账号。

### 11.5 自动测试

至少增加：

- 无 Token 访问首页时看不到主页面和底部导航。
- 有效 Token 通过 session 校验后显示页面。
- 伪造 Token 被清除并跳转登录页。
- 过期 Token 被清除并跳转登录页。
- session 校验故意延迟时，页面不会闪现受保护内容。
- session 校验遇到网络错误时显示重试，不误删 Token。
- 点击退出登录后回到登录页。
- 退出后直接访问 `/focus` 或 `/profile` 仍回到登录页。
- 后端 Token 过期边界具有单元测试。

### 11.6 验收标准

- [ ] 未登录不能看到主页面和底部导航。
- [ ] 页面不会先闪现内容再跳登录。
- [ ] 无效和过期 Token 会清除并跳转。
- [ ] 网络错误可以重试，不误判成退出。
- [ ] 用户可以主动退出登录。
- [ ] 退出后不能继续访问受保护页面。

## 十四、人工验收流程

第二阶段完成后，使用测试环境按顺序验收：

1. 启动后端和正式 Next.js 前端。
2. 不登录直接访问首页，确认只看到登录页。

8. 重新打开页面，确认自动结算且只增加一次。
9. 模拟保存失败，确认页面显示重试且统计未增加。
10. 恢复后端并点击重试，确认只增加一次。

15. 检查浏览器控制台没有 hydration mismatch 或未处理错误。
16. 运行 `./scripts/verify.sh`，确认全部通过。
17. 确认真实数据目录、真实 `.env` 和线上服务没有被测试触碰。

## 十五、安全与数据保护规则

- 修改任何 JSON 结构前，先保留只读备份或匿名样本。
- 不删除 `stats.json`，它是 P0-C 数据迁移前的核对材料。
- 不把真实邀请码、Token、用户 ID 或历史内容写入测试。
- 日志不得打印完成请求的 Authorization、邀请码或签名密钥。
- 结算失败不能吞掉错误并返回成功。
- sessionId 只能用于幂等，不能被当作用户身份。
- Token 仍按当前用户隔离规则验证，不能相信前端传来的 userId。
- 自动测试不能调用真实模型、真实 TTS 或生产 API。
- 不在本阶段执行线上数据清理和迁移。

## 十六、风险与回退方案

| 风险 | 预防措施 | 回退方式 |
|---|---|---|
| 历史统计突然变化 | 上线前用匿名样本对比新旧结果，记录合理差异 | 回退统计读取逻辑，保留 history 原文件 |
| history v2 写入错误 | 兼容读取旧结构，单文件原子更新 | 回退代码，原 JSON 和备份均保留 |
| 前后端发布顺序导致 422 | 前端先发送 sessionId，再收紧后端必填 | 临时恢复后端兼容字段并重新发布 |
| 重复补结算 | 后端以用户范围内 sessionId 幂等 | 关闭前端自动补结算，保留手动重试 |
| 结算失败丢状态 | 失败时保留 sessionId 和 pending 状态 | 用户继续使用同一 sessionId 重试 |
| 语音关闭后仍播放 | Provider 统一持有请求和 Audio | 暂时全局关闭 TTS，不影响文字功能 |
| 登录校验服务暂时不可用 | 网络错误显示重试，不直接删 Token | 保留登录页重试入口 |
| 页面仍出现 hydration 提示 | 首屏只使用固定默认值，挂载后读浏览器状态 | 回退单项组件改动，不回退后端数据修复 |
| JSON 多实例并发写入 | 明确只承诺当前单实例；P0-C 尽快迁移数据库 | 暂停扩大用户，不宣称多实例安全 |

所有回退都通过 Git 完成，不直接覆盖或删除真实数据。
